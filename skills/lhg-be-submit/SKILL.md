# lhg-be-submit：商店上架

> 目标：插件从"能跑"到"能上架"——物料齐、上架流程清、审核驳回有预案。
> 本 skill 的"上架 checklist"与"驳回预案表"为本插件原创整理；
> 商店政策以各官方最新文档为准，政策变化时以官方为准。

## 1. 何时使用

- 插件代码写完、准备上架或分发时 → 加载本 skill
- `/browser-ext-audit` 通过后 → 按第 3 节准备上架物料
- 审核被驳回时 → 按第 6 节对表处理

## 2. 输入与输出

- **输入**：插件目录（已通过审计，零 blocker）
- **输出**：上架物料包（zip + 图标 + 截图 + 商店文案 + 隐私政策）与分发方案
- **必须人工**：开发者账号注册、商店后台提交、审核答辩——AI 做不了，提前告知

## 3. 上架 checklist（逐项打勾）

### 3.1 代码与审计
- [ ] `ext_audit.py` 零 blocker（BE-MV2/BE-ICON/BE-CSP/BE-SEC 全过）
- [ ] manifest 的 name/description/version 完整（BE-HYG-001）
- [ ] 无 console.log 调试残留，无测试代码

### 3.2 图标（缺一不可）
- [ ] 16px / 48px / 128px 三档齐全（128 为商店必填，BE-ICON-002）
- [ ] PNG 格式，图标与插件功能相关，不蹭大厂 Logo
- [ ] 另备 1 张 440×280 商店头图（Chrome 应用商店展示用，可后期补）

### 3.3 商店文案
- [ ] 标题：功能直述，不许"最好""第一"等极限词
- [ ] 简介：3 句话说清"解决什么场景+怎么用+权限为什么需要"
- [ ] 权限说明：每个权限一句话用途（与 PERMISSIONS.md 一致）
- [ ] 详细介绍：功能列表 + 使用截图 + 更新日志入口

### 3.4 隐私与合规
- [ ] PRIVACY.md 已写：收集什么数据、存哪、是否上传、联系方式
- [ ] 申请了敏感权限（storage/identity/cookies/tabs/history）→ 商店后台隐私声明必填
- [ ] 无远程代码、无混淆到不可读（审核要看源码，过度混淆会被要求提供未混淆版）

### 3.5 截图与演示
- [ ] 至少 1 张功能截图（1280×800），展示核心界面
- [ ] 有 popup 的截 popup，有页面效果的截 before/after 对比
- [ ] 截图无个人隐私信息（账号、邮箱打码）

## 4. 三大商店差异

| 项 | Chrome 应用商店 | Edge 外接程序 | Firefox Add-ons |
|---|---|---|---|
| 开发者费用 | 一次性 $5 | 免费（需微软账号） | 免费 |
| 审核时长 | 数小时~数天 | 数天 | 数天~数周（人工严） |
| manifest | MV3 | MV3（与 Chrome 基本通用） | MV3 部分支持，需测 |
| 特殊要求 | 隐私政策必填（敏感权限） | 与 Chrome 类似 | 源码提交要求严 |
| 备注 | 国内访问需网络条件 | 国内可正常访问 | 小众但审核最严 |

**建议**：先上 Edge（免费、审核相对快）验证流程，再上 Chrome；
Firefox 按需适配（部分 chrome.* API 差异需实测）。

## 5. 打包与分发

```bash
# 打包：zip 插件目录（不含 .git/设计稿等无关文件）
cd my-ext && zip -r ../my-ext-v1.0.0.zip . -x "*.git*" "*.DS_Store"
```

- **商店分发**（推荐）：走官方商店，用户信任度最高，自动更新。
- **自托管分发**：官网提供 zip + 安装说明（Chrome 需开开发者模式加载已解压的扩展程序，
  每次重启会提示，不如商店体验）。
- **版本号纪律**：每次更新升 version，写更新日志；商店审核中的版本不要反复撤回重提。

## 6. 审核驳回预案（常见 5 种）

| 驳回理由 | 真实含义 | 处理 |
|---|---|---|
| 权限使用不明 | 权限说明没写清 | 重写权限用途，逐条对应功能截图 |
| 隐私政策缺失 | 申请了敏感权限 | 补 PRIVACY.md + 商店后台隐私声明 |
| 功能描述不符 | 实际功能与文案不一致 | 文案照实际功能改，或补功能 |
| 含混淆代码 | 审核看不懂 | 提供未混淆源码，或去掉混淆重提 |
| 单一用途违规 | 插件功能与描述差异大/捆绑无关功能 | 拆小：一个插件只做一件事 |

**心态**：驳回是常态，按意见改就是；同一问题被驳回两次就停下来重读政策，
不要反复提交碰运气（会被标记）。

### 6.5 更新与运维

上架不是终点，v1.0 之后：

- **版本节奏**：修 bug 随时发小版本；加功能攒 2~3 个发一次 minor，避免频繁打扰用户更新。
- **更新日志**：每个版本写 3 行以内的 changelog（修了什么/加了什么），商店后台必填，用户看得见。
- **用户反馈**：商店评论区是第一手需求来源；每周看一次，高频问题排进下个版本。
- **政策跟进**：Chrome 每年有 1~2 次扩展政策调整（如 MV2 下线）；收到政策邮件先读 lhg-be-mv3 对应章节，再改代码。
- **回滚**：商店支持回滚到上一版本；线上事故先回滚再修，不要在线上试错。

## 7. 上架交付报告（固定格式）

```markdown
# 《插件名》上架报告
- 审计：blocker 0 / warning 0（ext_audit.py）
- 物料：zip（xx KB）+ 图标三档 + 截图 2 张 + 商店文案 + PRIVACY.md
- 目标商店：Edge（先）→ Chrome（后）
- 需人工（按顺序）：
  1. 注册开发者账号（Chrome $5 / Edge 免费）
  2. 商店后台新建项，上传 zip
  3. 填文案/权限说明/隐私声明，传截图
  4. 提交审核，等结果（数小时~数天）
  5. 驳回按第 6 节处理
- 已知问题：Firefox 未适配（v1.1 再做）
```

## 8. 反模式

- ❌ 代码没审计就打包：blocker 上架 = 审核秒拒
- ❌ 图标随手画一张：128 图标缺失是最常见的上架卡点之一
- ❌ 权限说明写"需要这些权限才能运行"：等于没写，必被追问
- ❌ 文案夸大："最好用的翻译插件" → 极限词直接驳回
- ❌ 反复提交碰运气：会被审核标记，越急越慢

## 9. 自检与反馈

- [ ] checklist 3.1~3.5 逐项打勾

- [ ] 交付报告已给用户，"需人工"事项编号列出
- [ ] 未承诺"包过审"：审核以官方最新政策为准

**标准冒烟用例**：对 fixtures/be-good 跑上架流程 → checklist 应全过，
交付报告可生成。

**一键反馈**：遇到新的驳回理由或政策变化，以 `[QC] <一句话>` 为标题提交到
https://github.com/lhg-plugs/lhg-browser-ext/issues，正文写清"驳回原文 →
处理过程 → 最终结果"。
