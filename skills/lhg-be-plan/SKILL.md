# lhg-be-plan：插件需求规划

> 目标：把用户一句话的"想做个浏览器插件"变成可执行的功能范围——
> 先判定 MV3 能不能做，再定权限清单，最后才写代码。
> 本 skill 的"能力边界判定表"与"权限最小化设计流程"为本插件原创方法论。

## 1. 何时使用

- 用户说"做个浏览器插件/Chrome 插件"时 → 先加载本 skill 做需求规划
- 用户想法很发散时 → 用第 4 节收敛功能范围
- 审计报 BE-PERM-001/002（权限过度）时 → 回到本 skill 重做权限设计

## 2. 输入与输出

- **输入**：用户一句话想法（+ 可选：目标浏览器、目标网站）
- **输出**：功能范围说明书（含"做不了"清单 + 权限清单 + 功能拆分）
- **不输出**：代码（那是 lhg-be-mv3 的事）

## 3. MV3 能力边界判定（先判定，再承诺）

接到想法后，先过这张表。**标 ❌ 的必须在第一时间告诉用户做不了**，
不要等代码写一半才说。

| 用户想要 | MV3 能否做 | 说明 |
|---|---|---|
| 改页面样式/内容 | ✅ | content script，天生擅长 |
| 划词翻译/取词 | ✅ | 选中文本 + 浮层，见 lhg-be-features |
| 快捷键操作 | ✅ | commands API |
| 屏蔽页面元素 | ✅ | content script 删 DOM；大规模用 declarativeNetRequest |
| 跨站数据抓取展示 | ✅ | host_permissions + fetch（需用户装后授权） |
| 右键菜单 | ✅ | contextMenus API |
| 定时提醒 | ✅ | alarms API（service worker 会被休眠，不许用 setInterval） |
| 拦截修改网络请求 | ⚠️ 部分 | declarativeNetRequest 可按规则拦截改写；动态改请求体受限 |
| 常驻后台长连接 | ❌ | service worker 5 分钟无事件即休眠，做不了常驻 |
| 读取浏览器历史/密码 | ❌ | history 可读（需权限+审核严），密码读不到 |
| 操作本地文件 | ❌ | 扩展够不到本地文件系统（Native Messaging 例外，复杂度极高） |
| 手机浏览器上用 | ❌ | Chrome 安卓版不支持扩展（Kiwi 等第三方浏览器除外，不建议） |
| 自动登录/代填密码 | ⚠️ | 技术上能填，但涉及账号安全，见第 6 节红线 |

**话术模板**："你这个想法里 A、B 都能做，C 做不了（MV3 限制：…），
替代方案是 D，你看接受吗？"

## 4. 需求澄清（≤5 个问题）

1. 这个插件解决什么具体场景？（越具体越好："看文档时划词翻译"优于"做个翻译插件"）
2. 在哪些网站上用？（决定 content script 的 matches 范围——越窄越好）
3. 需要弹窗界面吗？（要 → action popup；不要 → 后台默默工作）
4. 需要存数据吗？存什么？（决定 storage 用法与隐私政策）
5. 将来要上架应用商店吗？（要 → 从第一天按 lhg-be-submit 的规范写）

## 5. 功能范围说明书（固定格式）

```markdown
# 《插件名》功能范围 v1.0
- 一句话：划词翻译——选中英文单词，浮层显示中文释义
- 目标浏览器：Chrome / Edge（MV3 通用）
- 功能拆分：
  1. content script 监听选中文本（matches: 全站，见权限说明）
  2. 浮层展示释义（调用免费词典 API）
  3. popup 设置页：开关、API 选择
- 做不了的：PDF 内划词（Chrome PDF 查看器进不去 content script）→ 替代：右键菜单查词
- 权限清单：
  | 权限 | 用途 | 能否更小 |
  |---|---|---|
  | activeTab | 读取选中文本 | 否（最小已是 activeTab） |
  | storage | 存用户设置 | 否 |
  | host_permissions: api.dict.example.com | 查词典 API | 否 |
- 隐私：不收集浏览数据，见 PRIVACY.md
```

**铁律**：
- 权限清单必须逐条写"用途"，写不出用途的权限不许申请（BE-PERM-001 的由来）。
- `host_permissions` 能写具体域名就不写 `<all_urls>`（BE-PERM-002）。
- "做不了"清单不许空着——空着等于没做边界判定。

### 5.5 权限设计速查表

| 权限 | 典型用途 | 审核敏感度 | 能否更小 |
|---|---|---|---|
| activeTab | 读取/操作当前标签页 | 低 | 已是最小 |
| storage | 存设置/缓存 | 低 | 否 |
| scripting | 向页面注入脚本 | 中 | 能用 content script 声明式注入就不用 |
| tabs | 读标签页标题/URL | 高 | 多数场景 activeTab 够用 |
| history | 读浏览历史 | 极高 | 非必需不申请 |
| cookies | 读写 Cookie | 极高 | 非必需不申请 |
| declarativeNetRequest | 按规则拦截请求 | 中 | 需配规则文件 |
| contextMenus | 右键菜单 | 低 | 否 |
| alarms | 定时任务 | 低 | 否 |
| notifications | 桌面通知 | 中 | 否 |

**设计流程**：先列功能需要的最小权限 → 逐条填用途 → 问"不申请能跑吗" →
能砍就砍 → 剩余权限进 PERMISSIONS.md。

**host_permissions 单独一列**：只在需要跨站 fetch 时申请，写具体域名；
`<all_urls>` 是最后手段，用了必须在说明书里写豁免理由。

### 5.6 最小可用插件（MVP）界定

小白第一个插件，建议 scope 压到这个形状：

- 1 个核心功能（四类脚手架之一，见 lhg-be-features）
- 权限 ≤3 个，无 `<all_urls>`
- 有 popup 或没有，二选一，不要"既要后台又要弹窗又要右键菜单"
- 不上架也行：先本地"加载已解压的扩展程序"自用，跑顺了再走商店

MVP 跑通的标准：自己连续用 3 天没想卸载。达不到就继续砍功能，不要加功能。

## 6. 合规与安全红线

- ❌ 代填密码/自动登录他人账号：触碰账号安全，不做
- ❌ 静默收集浏览历史上传服务器：除非用户明确知情同意 + 隐私政策，否则不做
- ❌ 远程代码执行：MV3 禁止从远程加载可执行代码（BE-CSP-001），更新逻辑走商店发版
- ❌ 伪装成官方插件：名称/图标蹭大厂品牌，上架必被下架且可能封号

## 7. 反模式

- ❌ 权限大礼包：一上来就要 tabs+`<all_urls>`+cookies → 审核被拒、用户不敢装
- ❌ 功能大杂烩："翻译+去广告+截图+笔记" → 小白 3 天做不完，先做最小可用
- ❌ 跳过边界判定：写到一半发现 MV3 做不了 → 返工成本最高
- ❌ 无隐私政策：申请了 storage/identity 却无 PRIVACY.md → 上架被打回（BE-PRIV-001）

## 8. 自检与反馈

**质检门**：
- [ ] 能力边界判定表已过，"做不了"清单非空或明确声明"无"
- [ ] 功能范围说明书已输出，用户已确认
- [ ] 权限清单逐条有用途说明，无 `<all_urls>`（或有豁免理由）
- [ ] 澄清问题 ≤5 个

**标准冒烟用例**：输入"做个划词翻译插件" →
应输出功能范围说明书，权限含 activeTab+storage，无 tabs/`<all_urls>`。

**一键反馈**：遇到边界表没覆盖的能力问题，以 `[QC] <一句话>` 为标题提交到
https://github.com/lhg-plugs/lhg-browser-ext/issues，正文写清"想做什么 →
查到的 MV3 限制 → 期望的判定结论"。
